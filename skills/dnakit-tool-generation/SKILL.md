# DNAKit 新工具生成

当用户提出 DNAKit 可能还不能完成的功能时使用本 Skill。目标是先确认现有能力，再为确实需要的功能实现一个可复用的候选工具；如果该候选包含多个可以独立调用、测试和复用的能力，则实现由多个子工具组成的候选工具集。

## 适用条件和边界

- 使用本 Skill 前，调用方需要准备好已经 clone 并固定 commit 的 DNAKit 候选代码目录（staging worktree）。仓库 URL、基线 commit 和 worktree 路径由运行配置提供，不写死在通用 Skill 中。
- 使用预先配置好的 `admet_ai` 环境。不要安装或升级依赖；缺少依赖应报告为环境预检问题。
- 不得修改正式的 `src/dnakit/generated/manifest.json`、隐藏测试、评分代码、独立评测程序或使用者代码目录。
- 使用 DNAKit MCP（或等效的 DNAKit CLI/API）搜索和调用已有工具；只在候选目录中编辑代码并运行公开检查。
- 不要读取隐藏测试、参考答案和后续复用任务。
- 只保留本地候选修改，不要自动执行 `git commit`、`git push`、创建 Pull Request 或向远程仓库提交代码；候选由独立评测程序读取和冻结。

## 第一阶段：先查已有工具

先输出一份计划，不要马上修改代码。计划需要由负责评测的控制程序或用户确认后，才能进入实现阶段。

1. 把需求说清楚：需要什么输入和输出、可能出现什么错误、有哪些参数限制、是否有副作用，以及以后可能怎样复用；同时识别需求中是否包含可以独立调用的能力。
2. 使用 `search_dnakit_tools` 搜索几个相关说法。若需求更像一个工作流，再使用 `search_dnakit_skills` 查找现成流程。
3. 对每个可能的工具调用 `describe_dnakit_tool`，查看名称、输入输出格式（JSON Schema）、参数限制、依赖和副作用。
4. 用公开示例调用候选工具的 `call_dnakit_tool`。如果任务允许组合多个已有工具，也要按允许的方式试一次。
5. 对照需求检查实际结果：已有工具是否已经能完成，是否需要组合，或者确实少了一项能力。
6. 先排除搜索词不合适、参数写错、凭据缺失、服务故障和依赖不可用等情况。这些问题不能作为新工具的理由。
7. 在计划中说明属于哪一种情况：`existing_capability`（已有工具可以完成）、`workflow_wrapper`（组合已有工具）、`controlled_recovery`（先解决环境问题）或 `new_function`（确实需要新增能力）。

只有在直接调用和所有允许的已有工具组合都无法满足需求，并且确认 DNAKit 确实没有这项能力时，才能提出 `new_function`。如果 MCP 或等效接口不可用，或者检查不完整，就停留在计划阶段并说明“还没有确认是否需要新工具”；不要编造工具名，也不要直接声称不存在可用工具。

只有同时满足下面条件，才把某项能力作为独立的新工具继续实现：

- 输入、输出、参数限制和异常可以写成稳定的接口；
- 功能不只是已有工具换一个名字或改几个参数；
- 功能可以处理不止一个公开示例，并且预期能在新的输入或任务中复用；
- 可以用独立参考实现、性质测试或差分测试验证结果；
- 依赖和副作用可以明确记录。

### 候选工具的粒度

默认交付一个可复用的候选工具。Plan 阶段必须检查这个候选是否包含多个可以独立调用、独立测试并在其他输入或任务中复用的能力：

- 如果只有一个能力满足条件，就实现一个候选工具；
- 如果多个能力都满足条件，就把它们拆成多个候选子工具，每个子工具都有独立名称、输入输出接口、错误处理、依赖说明和测试；
- 如果某部分只是实现细节、数据转换或无法脱离主流程复用的辅助步骤，就保留为内部函数，不单独注册；
- 如果需要一次调用完成完整流程，可以在基础子工具之外提供组合工具，但组合工具不能代替子工具的独立接口和测试。

工具名称、数量、拆分边界和接口必须根据当前需求、已有 DNAKit 约定和复用场景确定，不得在本 Skill 中预设具体领域名称或固定拆分方案。

如果需求只是几个已有工具的固定组合，应归为 `workflow_wrapper`；如果主要是操作步骤、参数选择或解释说明，应使用 Skill 或工作流；如果是凭据、服务或依赖问题，应归为 `controlled_recovery`。这些情况都不进入新工具实现阶段。

## 第二阶段：写出计划

计划至少要包含：

- `task_id` 和完整需求契约；
- `classification` 及简短理由；
- 所有搜索词，以及候选工具或 Skill 名称；
- 每个候选的输入输出格式、依赖、副作用和参数摘要；
- 尝试过的公开调用或工具组合、所用输入，以及观察到的输出或异常；
- 说明为什么已有工具不能完成，以及为什么问题不是环境故障或搜索失败；
- 说明为什么候选功能具有独立接口、跨输入或跨任务复用价值，并且不是简单别名或固定工作流；
- 说明最终是一个候选工具、多个子工具，还是子工具加组合工具，并解释每个边界；
- 每个候选工具的名称、输入输出 JSON Schema、异常、副作用、依赖、实现步骤和公开测试；
- 如果存在多个候选工具，说明它们之间的输入输出关系、依赖顺序和组合方式；
- 隐藏测试的边界、注册交接和 MCP 重启后的检查步骤，但不能包含隐藏测试内容。

只写“没有找到合适工具”不够。计划必须包含搜索、描述和调用记录，否则不能进入实现阶段。

## 第三阶段：实现候选工具

计划确认后，在候选代码目录中实现计划确定的最小候选工具或工具集。遵守仓库的工具接口和命名约定。每个对外暴露的候选工具都必须有独立接口和机器可读的输入输出契约；共用的数据读取、校验和转换逻辑可以放在内部模块中，不因存在内部函数就自动注册新工具。可以继续只读地使用 MCP，也可以运行公开测试，但不得修改 manifest 或独立评测程序。

在 `admet_ai` 中运行公开测试、静态检查和接口检查。记录命令、结果、修改文件、依赖假设和已知限制，并把候选代码和过程记录交给独立评测程序。

## 第四阶段：独立验收和修复

候选代码交给独立评测程序后，评测程序必须读取候选代码的冻结副本进行检查，不得替候选代码打补丁，也不得修改隐藏测试、评分器或正式 manifest。若候选是多个子工具，评测程序必须分别检查每个子工具，并检查允许的子工具组合。独立评测至少应覆盖接口、公开测试、静态检查、数值正确性、边界输入、结果完整性和跨输入复用。

如果评测失败，失败报告应回传给负责实现的 Agent，进入修复轮次。修复轮次遵守以下规则：

1. 只根据评测程序允许公开的诊断信息定位问题；隐藏测试的具体输入、参考答案和未公开断言不能泄露给 Agent。
2. 只在 staging worktree 中修改候选代码和过程记录；不得修改独立评测程序、隐藏测试、正式 manifest 或使用者代码。
3. 修复后重新运行公开测试、静态检查、接口检查和独立评测；不能只运行上一次失败的单项检查。
4. 每一轮都保存候选代码快照、变更说明、测试日志和评测结果，保证能够比较每轮结果；评测器应从新的冻结快照开始检查。
5. 由运行配置设定最大修复轮数。达到上限仍未通过时停止，并报告最后一次失败原因；不能为了通过验收而放宽测试或篡改参考结果。
6. 只有独立评测全部通过后，才可以为通过的候选工具逐项登记 manifest、重启 MCP，并进行全新的使用者 Agent 复用测试；工具集中的任一子工具或必要组合未通过时，不得部分注册或让使用者 Agent 发现候选工具。

如果当前运行配置没有提供可调用的独立评测命令或修复轮次控制器，Agent 可以完成候选实现和公开检查，但必须明确报告“尚未完成独立验收”，不能自行宣布通过或修改 manifest。

是否确实需要新工具、需要一个工具还是多个子工具、是否通过独立或隐藏测试、是否登记 manifest、是否重启 DNAKit MCP，以及如何用全新的使用者 Agent 测量复用，都由独立评测程序和运行控制器决定。复用测试时，不要把候选工具名或“需要新工具”的结论提前提供给使用者 Agent。
